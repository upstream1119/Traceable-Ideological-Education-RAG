# 严欣浩 P1 展示层图件路线图

## 1. 目标与边界

P1 的目标是形成两张可直接给组长和老师阅读的展示层图件，并让图件准确承接当前 KG-RAG 证据链：

1. `figures/p1_system_display_architecture.svg`：系统展示层架构图。
2. `figures/p1_web_sandbox_wireframe.svg`：Web 时空沙盘页面草图。

P1 只制作图件及其可核验说明，不实施正式前端，不接入真实接口，不开发完整 Three.js/XR，不实现 TTS 或数字人运行功能。

本阶段的核心原则是：图件服务于“可溯源证据检索底座”的解释，不把规划能力描述为已完成能力。

## 2. 已核验输入与事实边界

### 2.1 当前已实现基础

- 当前思政史语料为 245 条 chunks：`text_chunks_sizheng_v1.jsonl` 196 条，`text_chunks_sizheng_v2.jsonl` 49 条。
- `/retrieve` 默认采用轻量检索；FAISS 是可选向量后端，负责人可通过 `DACHUANG_VECTOR_BACKEND=faiss` 与有效的 `DACHUANG_FAISS_INDEX_DIR` 启用。
- FAISS 未配置、索引缺失、API Key 缺失、Embedding 失败或维度不匹配时，系统回退到轻量检索，并保持 `/retrieve` 返回契约。
- 当前链路已包含检索、GraphSim、生成回答、citation、`source_check`、`policy_check`、`agent_trace` 与 `final_decision`。
- P0 已完成 8 个展示节点的时空映射，并保留真实 chunk ID、citation、映射依据及验证状态。

### 2.2 必须保持的表述边界

- FAISS 当前属于工程冒烟与验收对比能力，不是论文实验结论，也不是默认检索后端。
- GraphSim 用于实体扩展与路径解释，不等同于完整知识图谱推理。
- Web 时空沙盘、TTS、数字人与 XR 是展示层承接方向，不是当前已实现的完整产品。
- `policy_check` 不替代专家审查。
- 前端不得因存在 `answer` 就直接展示或播报；必须遵从 `final_decision`。

## 3. 图件一：系统展示层架构图

### 3.1 图件目标

架构图要让非技术老师在一次阅读中理解：用户问题如何经过证据检索、生成与审查，再被安全地承接到 Web、数字人和 XR 展示层。

### 3.2 固定分层

图中必须从左到右呈现下列三层，并使用标题、边框或图例清楚区分：

| 分层 | 图中内容 | 表达要求 |
| --- | --- | --- |
| 当前已实现 | 用户问题、`/retrieve`、默认轻量检索、可选 FAISS、GraphSim、`hybrid_hits`、生成回答、citation、两类审查、`agent_trace`、`final_decision` | 使用实线，表示当前链路中的真实能力。 |
| P1 展示层承接 | 地图点、时间线事件、citation 卡片、流程状态、回答展示控制 | 使用实线或明确的“P1 图件设计”标签，不能伪装为已上线前端。 |
| 未来课堂展示 | TTS、字幕、轻量数字人讲解、XR/时空沙盘 | 使用虚线或“未来”标签，表示后续方向。 |

### 3.3 必须呈现的主链路

```text
用户问题
-> /retrieve
-> 默认轻量检索 / 可选 FAISS
-> GraphSim
-> hybrid_hits
-> 生成回答 + citation
-> source_check
-> policy_check
-> agent_trace
-> final_decision
-> Web 地图 / 时间线 / citation 卡片 / 输出与播报控制
-> 未来 TTS / 字幕 / 轻量数字人 / XR
```

### 3.4 `final_decision` 约束

架构图必须明确标出以下输出闸门：

- `approved`：允许展示正式回答，并允许后续 TTS 或数字人播报。
- `needs_review`：仅显示待人工复核状态和原因，禁止播报。
- `blocked`：禁止回答播报，显示阻断原因。

## 4. 图件二：Web 时空沙盘页面草图

### 4.1 图件目标

页面草图要说明 Web 原型的第一屏如何容纳检索、证据、时空展示和输出控制，使老师能看懂用户从提问到查看证据的完整过程。

### 4.2 固定页面区域

草图必须包含以下区域及其职责：

| 区域 | 职责 | 关键输入或状态 |
| --- | --- | --- |
| 提问与结果摘要区 | 输入问题并显示当前回答或复核/阻断状态 | `query`、`answer`、`final_decision` |
| 地图区 | 显示可信地标与高亮状态 | GeoJSON 地标、映射后的 `target_landmark_id` |
| 时间线区 | 显示正式或 proposed 事件与选中状态 | 时间线 JSON、`target_timeline_id` |
| citation 卡片区 | 展示可溯源证据及分数 | `hybrid_hits`、`citation`、`vector_score`、`graph_score`、`hybrid_score` |
| 流程与审查状态区 | 展示检索、生成、溯源审查、红线审查的过程状态 | `agent_trace`、`source_check`、`policy_check` |
| 数字人讲解预留区 | 表示未来讲解出口和当前播报锁定状态 | `final_decision`、未来 TTS/字幕/数字人 |

### 4.3 联动规则

图中必须以箭头、编号或同色高亮关系说明以下联动：

1. 提问后调用 `/retrieve`，产生 `hybrid_hits`、审查结果和 `final_decision`。
2. citation 卡片根据实体和 P0 映射表高亮相应地图点与时间线事件。
3. 点击地图点时，时间线跳转或高亮关联事件，citation 区筛选关联证据。
4. 点击时间线事件时，地图定位或高亮关联地标，citation 区展示关联证据。
5. 点击 citation 卡片时，地图点和时间线事件反向高亮。
6. 无可靠地点证据的节点只能停留在时间线、人物或事件卡片中，不得被画成地图坐标。
7. 数字人区域只能在 `approved` 时呈现“允许播报”；其余状态必须呈现“禁止播报”。

## 5. 图件制作策略

### 5.1 格式与存放

- 主文件格式统一为 SVG，便于后续编辑、审查和导出 PNG。
- 两张 SVG 都放入本目录的 `figures/`。
- 后续如需要 PNG，仅作为 SVG 的导出版本，同样放入 `figures/`，不散放到 `docs/` 或 `scripts/` 根目录。
- 图中文字使用中文，英文保留为接口字段、文件名和状态枚举。

### 5.2 面向老师的可读性规则

- 使用左到右的稳定阅读顺序，避免交叉箭头遮挡主要链路。
- 用“当前已实现 / P1 承接 / 未来方向”替代抽象技术分层词。
- 每个区域只保留必要字段名；用中文释义辅助理解。
- 颜色只用于辅助区分，不能成为判断“当前/未来”或“允许/禁止”的唯一方式。
- 不使用夸大表述，例如“零幻觉已实现”“完整 XR 已完成”。

## 6. 执行顺序与检查点

1. 以最新 `main`、P0 文档和 P1 验收标准为唯一事实来源。
2. 先制作系统展示层架构图，核对链路、分层和 `final_decision` 输出闸门。
3. 再制作 Web 时空沙盘页面草图，核对区域、联动和无地点节点边界。
4. 逐项执行 P1 验收标准中的内容、真实性、可读性和 Git 范围检查。
5. 完成自检后，提交图件及必要说明到 `yanxinhao`，由组长复核。

## 7. P1 完成定义

只有同时满足以下条件，P1 才能完成：

- 两张 SVG 图件均已生成，且位于 `figures/`。
- 两张图均通过仓库外的 P1 验收标准。
- 图件能准确区分当前能力、P1 承接和未来方向。
- 没有修改 `src/`、`tests/`、`configs/`、`data/processed/` 或 `data/graph/`。
- 组长对图件的事实边界和展示重点无阻断性意见。
